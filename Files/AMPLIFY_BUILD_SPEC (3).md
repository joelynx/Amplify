# Amplify — Build Specification

**Audience:** the AI coding agent that will build this app.
**Status:** authoritative source for a full rewrite from scratch.
**Source materials condensed here:**
- The functional specification (the vision document, primary).
- The architecture blueprint of the previous PySide6 prototype (reference only — no code is being ported; logic shapes are reused where they were correct).
- The seed question database.

This document tells you *what* to build, *how* the pieces fit, and *which order* to build them in. It does not prescribe specific class names or file contents beyond the structural constraints below — you have latitude on naming, but you must respect the architecture and the data model.

> Do not silently invent design choices outside this document. If something is genuinely under-specified, stop and ask. The project owner does not want surprises.

> **Critical scope rule.** This codebase is a **runtime-only** desktop app. It does not call any LLM API, any embedding API, or any other external network service. All "derived data" (vector embeddings, solution outlines, the per-topic depth map) is **pre-generated externally** during a separate dev-cycle pipeline that is **out of scope for this build** and ships baked into the seed (§4). The runtime reads this data, writes none of it, and degrades gracefully when fields are absent.

---

## 1. Product summary

Amplify is a **desktop application** that helps a student or instructor practice questions intelligently. It turns a curated bank of LaTeX-formatted questions into:

1. **Generated problem sets** — random selections from the bank, filtered by taxonomy, source, type, tags, and difficulty, output as a typeset PDF (with `.tex` export and a fallback if compilation fails).
2. **Interactive practice sessions** *(Phase 2)* — timed, scored, hint-enabled in-app practice on a curated subset.
3. **Long-running statistics** about the user's consumption (which topics they've practiced, how often, how balanced, how difficult).
4. **A question browser** for ad-hoc filtering, mass tagging, and manual selection.
5. **A history of every generated paper and quiz**, with regenerate / re-export controls.

Amplify is single-user, offline by default, and runs locally with a bundled LaTeX engine. The original deployment context is the IIT Delhi – Abu Dhabi campus, but the app itself is institution-agnostic.

## 2. Tech stack and high-level architecture

### 2.1 Stack

- **Shell:** PyWebView (single window, native chrome, system file dialogs).
- **Backend language:** Python 3.11+.
- **Database:** SQLite (one file, in the app data directory).
- **Frontend:** **React + Vite + Tailwind**, with **shadcn/ui** for components (Card, Button, Dialog, Combobox, Tooltip, Sheet, Form, etc.). State management is local (`useState` / `useReducer`); a small global store (Zustand) for cross-page state (active theme, active subject, current generate-form draft).
- **PDF/TeX engine:** **XeLaTeX**, bundled as **TinyTeX** for macOS and Windows. On Linux, the app uses system XeLaTeX from `PATH`; if absent, the Generate button surfaces an error with install instructions (best-effort Linux support).
- **Charts:** **D3** (used directly with thin custom React components) for everything: pie / spider / heatmap / line / multiplicity histogram. **No matplotlib anywhere** (hard rule).
- **Calendar heatmap:** D3 + a small custom component (no `react-calendar-heatmap`).
- **Vector embeddings:** **3072-dimensional** float32 vectors generated by `gemini-embedding-002` **during the dev cycle, externally** (out of scope for this build). The runtime reads them as `BLOB` columns alongside the question, runs in-process cosine similarity (brute force is fine at < 100k questions), and **never generates them**. The runtime app has no LLM client, no embedding API client, and no API key. New questions added via seed augmentation (§4.2) carry NULL embeddings until the next official seed release; similarity search simply skips them.

> Note the absence of `app/embeddings/`. It was in an earlier draft and has been removed: there is no LLM/embedding code in the runtime. The pre-generation pipeline that produces `pre_db.embeddings.npz`, `pre_db.outlines.json`, and `pre_db.topic_depth.json` lives in a **separate repository** managed by the project owner and is not part of this build's scope.

The hard rules:

1. **The frontend never touches the file system or the DB directly.** Every read and every write goes through one `@expose`-d function in `app/ipc/api.py`. This is what makes the desktop wrapper interchangeable later.
2. **`app/core/` is pure** — no SQLite, no PyWebView, no filesystem. It takes inputs, returns outputs. It is the part you can unit-test offline.
3. **`app/persistence/` is the only place SQL lives.** Repositories return `app/core/models` objects, not rows. Migrations are forward-only, numbered, and live in `migrations/`.
4. **The IPC surface is finite and documented** (see §5). New features extend the IPC surface; the frontend may not invent its own data layer.

## 3. Data model (canonical)

The seed bundle (§4.1) defines the canonical question shape. The columns and their **canonical types** (post-ingestion, in SQLite):

### 3.1 `questions`

The taxonomy on a question is **three levels**: `topic → branch → subtopic`. There is **no `stream` and no `subject`** on the question itself. "Subjects" / "Courses" live in a separate table (§3.6) and *point* to topics — a question does not "belong" to a subject; it is included in a subject if and only if the active subject points to its topic and does not exclude its branch or subtopic.

| column                   | SQLite type    | source / notes                                                                                            |
| ------------------------ | -------------- | --------------------------------------------------------------------------------------------------------- |
| `question_id`            | INTEGER PK     | from sheet column `QuestionID`.                                                                           |
| `semester`               | INTEGER        | from sheet column `Semester`. Optional / nullable; it is metadata, not a hierarchy level.                 |
| `topic`                  | TEXT NOT NULL  | top of the in-question taxonomy.                                                                          |
| `branch`                 | TEXT NOT NULL  | stored *without* `[…]` brackets. (The seed has them; strip on ingest.)                                    |
| `subtopic`               | TEXT NOT NULL  |                                                                                                           |
| `latexcode`              | TEXT NOT NULL  | the raw LaTeX of the question body. **Never sanitized.**                                                  |
| `type`                   | TEXT           | one of `proof`, `numerical`, `explanation/reasoning` (extensible).                                        |
| `in_syllabus`            | INTEGER (0/1)  | **per-question manual exclusion override**, settable from the Browser via mass-action. Defaults to 1. Independent of subjects. |
| `source`                 | TEXT           | e.g. `IITD-AD`, `IITK`, `IITM`.                                                                           |
| `subsource`              | TEXT           |                                                                                                           |
| `answer`                 | TEXT           | the canonical answer (numerical, expression, or short text).                                              |
| `solution`               | TEXT           | LaTeX. Placement in PDFs is user-configurable (§6.5). Always available to interactive review.             |
| `solution_outline`       | TEXT           | Enumerated solution sketch for long solutions; **pre-generated externally and shipped as seed data** (§13.2). NULL when the question was not in the eligible set or was added later via seed augmentation. |
| `hints`                  | TEXT           | LaTeX. Used by interactive mode (Phase 2).                                                                |
| `instructions`           | TEXT           | **interactive-only** per-question instruction telling the user how to format a non-numerical answer for evaluation (e.g. "give your answer as a fraction p/q in lowest terms"). Not rendered in PDFs. |
| `date_last_accessed`     | TEXT (ISO8601) | UTC; updated on every successful PDF/quiz inclusion.                                                      |
| `times_used`             | INTEGER        | incremented on every successful PDF generation.                                                           |
| `interactive_times_used` | INTEGER        | incremented on every successful quiz inclusion.                                                           |
| `difficulty_rating`      | REAL (0–20)    | manual rating, plus the smart-difficulty score once Phase 2 is built.                                     |
| `latex_hash`             | TEXT UNIQUE    | SHA-256 of normalized (`\r\n` → `\n`, trailing whitespace stripped) `latexcode`. Used to deduplicate and to identify rows when matching seed companion files. |
| `classification_emb`     | BLOB           | float32 × 3072 (little-endian). **Seed data**, populated from `pre_db.embeddings.npz` at ingest. NULL for questions added later via seed augmentation. |
| `similarity_emb`         | BLOB           | float32 × 3072. Currently the same vector as `classification_emb` in the seed; the column pair is preserved for forward compatibility. |

> The legacy seed sheet has columns the current schema does not use (`Stream`, `Subject`, `AnsCode`). They are **dropped on ingest** — see §4.1. The runtime never sees them.

### 3.2 `question_tags` (M:N)

```sql
CREATE TABLE question_tags (
    question_id INTEGER NOT NULL,
    tag         TEXT    NOT NULL,
    PRIMARY KEY (question_id, tag),
    FOREIGN KEY (question_id) REFERENCES questions(question_id) ON DELETE CASCADE
);
```

The seed sheet stores tags as a Python-literal list in one cell. On ingest, parse with `ast.literal_eval` and explode into rows here.

### 3.3 `templates`

A *template* is a saved snapshot of the entire generation form so the user can re-apply it.

```sql
CREATE TABLE templates (
    name             TEXT    PRIMARY KEY,
    subject          TEXT,
    topic_list       TEXT,                  -- JSON list[str]
    branch_list      TEXT,                  -- JSON list[str]
    subtopic_list    TEXT,                  -- JSON list[str]
    type_list        TEXT,                  -- JSON list[str]
    source_list      TEXT,                  -- JSON list[str]
    tag_list         TEXT,                  -- JSON: {compulsory: [...], optional: [...], excluded: [...]}
    n_questions      INTEGER NOT NULL,
    reuse_questions  INTEGER NOT NULL,      -- 0/1
    include_sources  INTEGER NOT NULL,      -- 0/1
    in_syllabus_only INTEGER NOT NULL,      -- 0/1
    min_difficulty   REAL,
    save_directory   TEXT
);
```

Templates with the prefix `[PBS]` are reserved for the Physics-Brawl-Style interactive template (see §10).

### 3.4 `psets` and `pset_questions`

A *PSet* is one generated PDF.

```sql
CREATE TABLE psets (
    pset_id           TEXT    PRIMARY KEY,   -- the PDF filename (e.g. "Math_I_20251023_174530.pdf")
    date_created      TEXT    NOT NULL,
    subject           TEXT,
    topic_list        TEXT,                  -- JSON list[str]
    branch_list       TEXT,
    subtopic_list     TEXT,
    source_list       TEXT,
    type_list         TEXT,
    tag_list          TEXT,                  -- same shape as templates.tag_list
    n_questions       INTEGER NOT NULL,
    reuse_questions   INTEGER NOT NULL,
    template_name     TEXT,                  -- nullable, FK soft (templates can be deleted later)
    topic_dist        TEXT,                  -- JSON dict {topic: count}
    subtopic_dist     TEXT
);

CREATE TABLE pset_questions (
    pset_id        TEXT    NOT NULL,
    question_id    INTEGER NOT NULL,
    question_order INTEGER NOT NULL,
    PRIMARY KEY (pset_id, question_id),
    FOREIGN KEY (pset_id)     REFERENCES psets(pset_id)         ON DELETE CASCADE,
    FOREIGN KEY (question_id) REFERENCES questions(question_id) ON DELETE CASCADE
);
```

### 3.5 `quizzes` and `quiz_questions` *(Phase 2 — interactive mode)*

Same shape as PSets but with extra columns: `time_per_question`, `total_time`, `allow_skips`, `show_scoring`, `penalize_skips_marks`, `enable_hints`, `instant_scoring`, `show_solutions`, `gradient_mode` (`random`/`constant`/`custom`), `wait_for_correct` (the "phys" mode), and a `quiz_attempts` table to record per-attempt scoring.

### 3.6 `subjects` (also called Courses)

A **Subject** (alias **Course**) is *not* a property of a question. It is a saved bundle that **points to topics** and optionally **excludes specific branches and subtopics** within those topics.

A question is "in" a subject when:

1. The subject's topic list includes the question's `topic`, **and**
2. The question's `branch` is **not** in the subject's `excluded_branches[topic]`, **and**
3. The question's `subtopic` is **not** in the subject's `excluded_subtopics[topic][branch]`, **and**
4. The question's per-row `in_syllabus` flag is `1` (the manual override; see §3.1).

```sql
CREATE TABLE subjects (
    name      TEXT PRIMARY KEY,        -- e.g. "Math I", "MTL101 Calculus"
    payload   TEXT NOT NULL,           -- JSON; see below
    is_active INTEGER NOT NULL DEFAULT 0
);
```

Payload shape:

```json
{
  "topics": ["Single Variable Calculus", "Linear Algebra", ...],
  "excluded_branches": {
    "Single Variable Calculus": ["Sequences and Series"]
  },
  "excluded_subtopics": {
    "Linear Algebra": {
      "Eigenvalues and Eigenvectors": ["Diagonalization over C"]
    }
  },
  "description": "freeform notes",
  "schema_version": 1
}
```

There is **at most one active subject at a time** (`is_active = 1` for exactly zero or one row). The Generate page's "Subject" combobox selects the active subject from this table; "In syllabus only" filters use the active subject's payload to compute the eligible (topic, branch, subtopic) set.

The active subject is independent of the `questions.in_syllabus` flag. The flag is a per-question manual override the user can mass-toggle from the Browser (e.g. "this question is broken / out of date / not relevant"); the subject is a curricular boundary. Both must be satisfied for "in syllabus" to be true.

Subjects are import/export-able as JSON files (the payload, plus `name`).

> The legacy seed sheet's `Subject` column is **not used** by ingest in any way. It does not become a column on `questions`, and it does not bootstrap `subjects` rows. The `subjects` table starts **empty** on first launch; the user creates subjects manually (or imports JSON) on the `/subjects` page.

### 3.7 `configs`

Same key-value JSON store as the prior prototype:

```sql
CREATE TABLE configs (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL              -- json.dumps'd
);
```

Default keys, seeded on first run: `THEME_SELECTED`, `DEFAULT_NO_QUESTIONS`, `FILE_SAVE_LOCATION`, `LAST_USED_SUBJECT`, `PDF_LEFT_HEADER`, `PDF_RIGHT_HEADER`, `PDF_TITLE_LINE`, `PDF_INSTRUCTIONS`, `EMBED_MODEL_VERSION` (a string copied from the seed bundle for diagnostic display only — never used to drive runtime behavior), `APPNAME`, `VERSION`.

> **No API keys are stored in the runtime DB.** The runtime never makes outbound API calls; embeddings, outlines, and topic-depth values are all loaded from seed companion files (§4.1).

### 3.8 Migrations

Each schema change is a numbered SQL file in `app/persistence/migrations/`:
`001_initial.sql`, `002_add_solution_outline.sql`, ….

The `migrations` table records which have run.

## 4. Seed data and ingestion

The runtime is a consumer of two distinct kinds of input:

- The **shipped seed bundle** (§4.1), a set of read-only files that come with the app and represent the curated question bank. Loaded once on first launch into SQLite. Never modified by the runtime. Re-loadable on demand from Settings.
- **Augmentation CSVs** (§4.2), which the user can upload to add questions on top of the seed without going through a release cycle. Simpler than the seed bundle (no embeddings, no outlines), idempotent by `latex_hash`.

Both paths produce rows in the same `questions` table with the same shape. The only distinction is provenance metadata for diagnostics.

### 4.1 The shipped seed bundle

The seed lives in `app/data/seed/` and consists of:

| file                       | purpose                                                                                  | format                                                              |
| -------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `pre_db.xlsx`              | Primary question content. Multi-sheet (validation lookups + main).                       | .xlsx, header on row 2 (row 1 is type hints).                       |
| `pre_db.csv`               | Diff-friendly mirror of the main sheet of `pre_db.xlsx`. Auto-generated by ingest.       | UTF-8 CSV.                                                          |
| `pre_db.embeddings.npz`    | 3072-dim float32 vectors per question, generated by `gemini-embedding-002` externally.   | numpy `.npz` archive; key `vectors` shape `(N, 3072)`, key `question_ids` shape `(N,)` int64. |
| `pre_db.outlines.json`     | Pre-generated solution outlines for the eligible top-30% by solution length (§13.2).     | JSON object: `{"<question_id>": "<latex outline>"}`.                |
| `pre_db.topic_depth.json`  | Per-topic education depth on a 0–20 scale (§13.3).                                       | JSON object: `{"<topic name>": <int 0..20>}`.                       |

All five files are produced **outside this codebase** by a separate dev-cycle pipeline that the project owner manages. The build agent does not need to know how that pipeline works; it needs only to consume the artifacts.

**Initial-ingest algorithm.** On first launch (or on demand from Settings → "Re-run Seed Ingest"):

1. Open `pre_db.xlsx` with `openpyxl` (`read_only=True`). Skip the type-hint header (row 1); use row 2 as column names. Only the main sheet is ingested. Write a clean `pre_db.csv` mirror of the main sheet to `app/data/seed/` (overwriting any prior copy).
2. For each data row in the main sheet:
   - **Drop the `Stream` column.** Not ingested.
   - **Drop the `Subject` column.** Not ingested. (See §3.6 — `subjects` rows are user-created, not seeded.)
   - **Drop the `AnsCode` column.** Not ingested. (The field has historically held test-data values; it is reserved for a future re-introduction.)
   - Strip `[…]` brackets from the `Branch` cell.
   - Coerce `In Syllabus?` (`yes`/`no`/blank) to `0`/`1` and write to `questions.in_syllabus`. Default `1`.
   - Parse `Tags` with `ast.literal_eval` (it's a Python list literal). If it's empty / `N/A`, treat as `[]`.
   - Compute `latex_hash = sha256(normalize(latexcode))`. Skip the row if the hash is already in the DB (idempotent re-ingest).
   - Insert into `questions`; insert N rows into `question_tags`.
3. Load `pre_db.embeddings.npz`. For each `question_id` present in both the DB and the npz, write `vectors[i]` as a 3072 × 4-byte little-endian float32 BLOB into both `classification_emb` and `similarity_emb`. Questions whose `question_id` is **not** in the npz keep NULL in those columns and are silently skipped during similarity search.
4. Load `pre_db.outlines.json`. For each `question_id` key matching a row in the DB, write the value into `solution_outline`.
5. Load `pre_db.topic_depth.json`. Write the entire object verbatim into `configs.TOPIC_DEPTH_MAP`. (Used by smart difficulty in Phase 2; safe to ingest now and consume later.)

Steps 3, 4, 5 are best-effort: if a companion file is missing or malformed, log a warning and continue. Embeddings, outlines, and depth are *enrichment* — the app must be functional without them (similarity search returns empty lists; "Outline only" PDF placement falls back to full solutions; smart difficulty is gated behind a Phase 2 toggle anyway).

Re-ingest is **idempotent** and safe to re-run; it inserts only `latex_hash`-new rows.

### 4.2 User augmentation via CSV

The Settings page exposes **"Augment seed from CSV…"**. The user picks a CSV file with the same column shape as the main sheet of `pre_db.xlsx` (the dev-side authoring spec is "make a sheet that looks like `pre_db.csv`"). The ingest path is a strict subset of §4.1:

1. Read the CSV with the standard library `csv` module. The header is row 1 (no type-hint row, unlike the xlsx).
2. Apply the same per-row transformations: drop `Stream` / `Subject` / `AnsCode`, strip branch brackets, coerce `In Syllabus?`, parse `Tags`, compute `latex_hash`.
3. Skip rows whose `latex_hash` already exists in the DB (deduplication; idempotent across re-uploads).
4. Insert new rows into `questions` and `question_tags`. Their `classification_emb`, `similarity_emb`, and `solution_outline` are **NULL**. They will not appear in similarity-search results until a future seed bundle includes them.
5. Return a result dialog: `{added: N, skipped: M (already present), errors: [...]}`.

**No LLM, embedding, or external API is called during augmentation** — the app stays fully offline.

If the user wants the augmented questions to participate in similarity search, they must round-trip them through the external dev-cycle pipeline (out of scope for this codebase) and ship a new seed bundle.

## 5. The IPC surface (`app/ipc/api.py`)

Every name below is a function `@expose`-d to JS. Inputs are JSON-serializable; outputs are too.

### 5.1 Hierarchy / dropdowns

`subject` below refers to the *name of an active or selected Subject row* (§3.6), used to scope the eligible (topic, branch, subtopic) set. There is **no `stream` argument anywhere**.

```
get_topics(subject=None, in_syllabus_only=True)              -> list[str]
get_branches(subject, topic, in_syllabus_only=True)          -> list[str]
get_subtopics(subject, topic, branch, in_syllabus_only=True) -> list[str]
get_concept_tree(subject=None, in_syllabus_only=True)        -> nested dict for the tree widget
get_types()                                                  -> list[str]
get_sources()                                                -> list[str]
get_all_tags(filters=None)                                   -> list[str]   # see §7.3 for dynamic filtering
```

When `subject` is `None`, results span the entire DB (no curricular restriction). When `subject` is a name, results are restricted to the topics that subject points to and not in its excluded branches/subtopics. `in_syllabus_only` additionally restricts by the per-question `in_syllabus` flag.

### 5.2 Generation

```
count_matching_questions(filters)                     -> int
generate_pdf(filters, output_settings)                -> {success, pset_id, path, fallback?}
export_tex(filters, output_settings)                  -> {success, path}
get_random_questions(filters, n)                      -> list[Question]   # for previews / browser
```

### 5.3 Templates

```
list_templates()                                      -> list[str]
template_name_available(name)                         -> bool
load_template(name)                                   -> Template
save_template(name, payload)                          -> None
delete_template(name)                                 -> None
```

### 5.4 PSets / history

```
list_psets(subject=None, date_range=None)             -> list[PSetSummary]
load_pset(pset_id)                                    -> {questions, params}
delete_pset(pset_id)                                  -> None
re_export_pset_pdf(pset_id)                           -> {success, path}        # same questions, fresh PDF

It does *not* generate immediately — the user reviews and edits the filters first. The new PSet stores the *edited* filters; the source PSet is not linked.

### 5.5 Subjects (Courses)

```
list_subjects()                                       -> list[str]

## 6. PDF / TeX generation

### 6.1 Generation flow

A `generate_pdf(filters, output_settings)` call does, in order:

1. Validate `filters`: subject is required; tree must have ≥1 leaf checked; output directory must exist.
2. `selection.pick(filters, n)` returns a list of `n` question dicts (random order, no duplicates).
3. `pdfgen.assemble(questions, output_settings)` produces a `.tex` string.
4. Run XeLaTeX in a temp directory; capture stdout/stderr to the log.
5. On success: copy the PDF to `output_settings.directory`, named `Subject_YYYYMMDD_HHMMSS.pdf`, then atomically `INSERT INTO psets …` and N rows into `pset_questions`, then `UPDATE questions SET times_used = times_used + 1, date_last_accessed = now() WHERE question_id IN (…)`.
6. On compilation failure: write the `.tex` to the user's directory as a fallback, and return `{success: false, fallback: '<path>.tex', errors: '<tail of XeLaTeX log>'}`. The frontend shows a dialog with a clickable `file://` link.
7. Either way, return the result to JS so the frontend can route the user to the success modal or the failure modal.

### 6.2 Preamble

The preamble is fixed (no user input). Carry forward the prior prototype's set:

```latex
\documentclass{article}
\usepackage{amsmath}\allowdisplaybreaks
\usepackage{amsfonts}\usepackage{amssymb}\usepackage{caption}
\usepackage{graphicx}\graphicspath{{<image_path>}}
\usepackage{fancyhdr}\usepackage{geometry}\usepackage{enumitem}
\usepackage{circuitikz}\usepackage{chemfig}\usepackage{pgfplots}
\usepackage{mathtools}\usepackage{stmaryrd}\usepackage{ulem}
```

`<image_path>` resolves to `app/data/appdata/teximages/` with forward slashes (this matters for LaTeX even on Windows).

### 6.3 Sanitization for user-typed PDF heading content

User input flows into the **left header**, **right header**, **title line**, and **instructions block** — and only into those. Question bodies are *never* sanitized.

Three escalating sanitizers:

- **`escape_latex(text)`** — used for short defaults. Allows `\textbf`, `\texttt`, `\textsc`, `\textit`, `\underline`, `\emph`, inline math `$…$`. Escapes `\ { } $ & % # ^ _ ~`.
- **`sanitize_latex_basic(text)`** — used for **left/right header**. Adds whitelisted math (`\frac`, `\sqrt`, `\sum`, `\int`, `\lim`, Greek, `\mathbb/cal/bf/it/rm`, set/relation/arrow operators). Rejects `\input`, `\include`, `\newcommand`, `\renewcommand`, `\def`, `\let`, `\usepackage`, `\documentclass`, `\write`, `\openout`, `\closeout`, `\read`, `\verb`, `\verbatim`, `\lstinline`, `\lstinputlisting`, `\url`, `\href`, `\includegraphics`, `\label`, `\ref`, `\cite`, `\bibliography`, `\bibliographystyle`, plus `$$…$$`, `\[…\]`, and itemize/enumerate.
- **`sanitize_latex_extended(text)`** — used for **title line** and **instructions block**. Same as basic, plus display math `$$…$$` and `\[…\]`, `itemize`/`enumerate` (with optional `[label=…]`), and the underline family `\uline/\uuline/\uwave/\sout/\xout/\dashuline/\dotuline`.

These are pure functions; unit-test them with golden-file fixtures.

### 6.4 Header variables

The header text supports the following dynamic substitutions (carry forward from the prior prototype):

| token   | resolves to                                |
| ------- | ------------------------------------------ |
| `<S>`   | subject                                    |
| `<T>`   | comma-joined topic list                    |
| `<N>`   | number of questions                        |
| `<K>`   | comma-joined source list ("All" if empty)  |
| `<Q>`   | comma-joined question type list            |
| `<src>` | per-question source string (in body only)  |
| `<P>`   | PSet ID (== filename)                      |
| `<d>`   | date `DD-MM-YYYY`                          |
| `<D>`   | date `Day, DD Month YYYY`                  |

If the user picks a local image file (`.png/.jpg/.jpeg/.gif/.bmp/.svg`) for the left or right header, the input becomes read-only and the stored value is `\includegraphics[width=1cm]{<absolute path>}`. The trash button reverts to text mode.

### 6.5 Solution placement

Each generated PDF carries a user-selected solution placement chosen on the Generate page (also savable in templates). Options:

| value          | layout                                                                                                                             |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `none`         | questions only. (Default.)                                                                                                          |
| `appendix`     | questions in the body; a "Solutions" section follows after a `\newpage`, in the same order, each headed by `\textbf{Q\arabic{}}`. |
| `interleaved`  | each question is immediately followed by its solution before the next question. Useful for self-study sets and worked examples.    |
| `outline_only` | uses `solution_outline` (§13.2) instead of full `solution`, in either appendix or interleaved layout (controlled by a sub-toggle). |

The Generate page exposes a single "Solutions" combobox (`None / Appendix / Interleaved / Outline only`); when "Outline only" is chosen, a sub-toggle picks appendix-vs-interleaved.

Per-question `instructions` is **never** rendered into the PDF (it is interactive-only metadata; see §3.1).

Per-question `source` is rendered next to the question body if and only if the Generate page's "Include sources" toggle is on.

When `outline_only` is selected and a question has `solution_outline IS NULL`, the renderer falls back to that question's full `solution` and logs a warning.

## 7. Filtering and selection (the core algorithm)

### 7.1 Inputs

A `filters` object has the following shape:

```json
{
  "subject":          "Math I",                      // optional; null/missing = no curricular restriction
  "topics":           ["Calculus", "Sequences and Series"],
  "branches":         ["Single Variable Differential Calculus"],
  "subtopics":        ["Limits (Single Variable)", ...],
  "sources":          ["IITD-AD"],                   // empty/missing == ALL
  "types":            ["proof", "numerical"],        // empty/missing == ALL
  "tags": {
    "compulsory":     ["Mathematical Induction"],    // ALL must be present
    "optional":       ["Coloring Proof", "Diagram"], // at least ONE must be present (if non-empty)
    "excluded":       ["Off-syllabus"]               // NONE may be present
  },
  "min_difficulty":   0,
  "reuse_questions":  false,
  "in_syllabus_only": true
}
```

### 7.2 Semantics

The set of matching questions is the questions such that **all** of:

- If `subject` is set: the question's `topic` is in that subject's `topics`, AND its `branch` is not in that subject's `excluded_branches[topic]`, AND its `subtopic` is not in that subject's `excluded_subtopics[topic][branch]`.
- `(topic, branch, subtopic)` matches the **deepest** non-empty level provided in the filter form. The CheckableTree gives `subtopics` directly when leaves are checked; if a parent (topic or branch) is fully checked the tree may collapse the selection up to that level — both shapes must be supported.
- `source` is in `sources` (or `sources` is empty).
- `type` is in `types` (or `types` is empty).
- For tags: `(set(question.tags) ⊇ set(compulsory))` AND `(optional == [] OR set(question.tags) ∩ set(optional) ≠ ∅)` AND `(set(question.tags) ∩ set(excluded) == ∅)`.
- `difficulty_rating ≥ min_difficulty`.
- If `in_syllabus_only`: `questions.in_syllabus = 1` (the per-question manual override). When `subject` is also set, the curricular boundary above already restricts further; the two are independent gates that both must pass.
- If NOT `reuse_questions`: `times_used = 0`.

A tag in both `compulsory` and `excluded` is rejected by the API with an explicit error rather than silently returning zero rows.

### 7.3 Dynamic tag dropdown

When a user is composing the tag tray, the dropdown of available tags must be **dynamic**: it lists only tags `t` such that adding `t` to the current filter set would produce ≥1 matching question. This means the tag dropdown re-queries on every change to subject / tree / sources / types / difficulty / other tags. Same rule applies to sources and types when those are presented as searchable comboboxes.

### 7.4 Selection

Once the matching set is computed, `selection.pick(filters, n)`:

- Issues a single SQL `SELECT … FROM questions … ORDER BY RANDOM() LIMIT n`.
- If the matching set is smaller than `n`, return what exists and surface a warning (`{shortfall: 3}`) — do not silently undershoot without telling the UI.

### 7.5 Live "N questions match"

The main page shows a status-bar message that updates whenever any filter changes: e.g. `"237 questions match your current filters"`. This calls `count_matching_questions(filters)` debounced at ~150ms.

## 10. Interactive practice (Phase 2)

A quiz is configured via a settings panel that mirrors the spec's "Options" block:

- **Template** dropdown:
  - **`[PBS] Physics Brawl Style`** — special, locked layout (resets toggles when chosen; saving a tweaked copy prefixes `[PBS]`). See §10.1.
  - **`MIT Integration Bee`** — fully editable.
  - **`Free-Answering`** — fully editable.
- **Time** — per-question and/or total (independent toggles, except in `[PBS]` where only the total timer is allowed).
- **Number of questions** — the size of the question pool drawn from the filters.
- **Allow skips?** — disables next-question navigation if off.
- **Show scoring?** — display only; statistics still record scores even if hidden.
- **Penalize skips?** (visible only if skips + scoring are both on) + marks penalty.
- **Enable hints?**
- **Instant scoring?** — disables free navigation between questions; otherwise final score is shown only on the History review page.
- **Show solutions?** — only available if no timer; review page always shows solutions regardless.
- **Gradient** — points distribution: random / constant / custom.
- **Question type distribution** (`proof` / `numerical` / `explanation/reasoning`) — restricted in `[PBS]` mode (numerical only).
- **Wait for correct answer?** — the "phys" mode: do not move on until correct. Implies skips off. Disabled in `[PBS]`.

When a quiz finishes, an `attempt_id` is recorded, and the `/quiz/review/:id` page re-renders the questions with the user's answers, correct answers, hints, and solutions. The History page lists both PSets and quiz attempts.

### 10.1 `[PBS]` Physics Brawl Style — parallel widget pool

PBS is a distinctive runner. Properties:

- **No per-question timer.** A single **total timer** counts down. The quiz ends when either the timer reaches zero or the question pool is exhausted.
- **N widgets visible at once**, where N is configured at template creation (the "Number of widgets" input replaces "Time per question" in the locked panel). Each widget shows one question and an answer input.
- **Pool semantics:** at start, `pool` is filled with `pool_size` questions selected by the filters (where `pool_size > N`). Each visible widget is bound to one question dequeued from `pool`. When the user submits a correct answer, that widget is replaced by the next question dequeued from `pool` until `pool` is empty. After `pool` is empty, the widget collapses (greyed-out completed state).
- **Question type:** **numerical only** in PBS — enforced as `questions.type = 'numerical'` at template-creation time and at quiz-start time.
- **Hints:** disabled in PBS.
- **Skips:** allowed implicitly — the user may switch which widget they're working on at any time. A widget is only "consumed" when its current question is answered correctly. There is no explicit skip; if a question is too hard, the user can ignore that widget and work on the others, or guess (with the wrong-answer penalty below).
- **Scoring:**
  - Each correctly answered question awards points **linear in its `difficulty_rating`** (e.g. `points = round(difficulty_rating)` with a per-template multiplier).
  - **Wrong attempts on a single widget reduce that question's available score**, e.g. the available score halves on each wrong attempt before the eventual correct answer (or floors to 1, whichever is higher). The exact decay function lives in `app/interactive/scoring.py` and is parametrized; the default is geometric × 0.5.
  - No negative scores. A question never contributes less than 0.
- **Layout:** the N widgets are tiled (responsive grid; 2 columns on narrow viewports, up to 4 on wide). Each widget header shows the live "available score" for that question. The total score and the timer sit pinned at the top of the page.

### 10.2 Non-PBS runner

The non-PBS runner uses a single visible widget (`slot_index = 0`) and progresses through the question pool one at a time, governed by the configured `Allow skips` / `Wait for correct` / `Instant scoring` flags.

- `sprites/` — replacements for icons that are *thematic* (cursor, button glyphs, navigation arrows). Functional icons stay neutral.
- `sounds/` — `click.mp3`, `generate.mp3`, `error.mp3`, `success.mp3`, `theme_switch.mp3`.

Switching themes re-applies CSS variables, swaps the active sprite directory referenced in `<img>` `src` attributes, and changes the sound pack used by `play_sound(event)`. **No reload required.**

### 11.3 Tokens

Every theme defines, at minimum:

```
--text  --background  --surface  --primary  --secondary  --accent
--border  --muted  --success  --warning  --error
--rem (the "1 unit = font-size" convention from the prior prototype)
--font-family
```

Color preferences (per the spec) are editable independently of the theme via the Settings page — i.e., the theme provides a default, and the user can override any token without leaving the theme.

### 11.4 Pixel Art / Windows XP — caveat

The spec treats these as flavors, not pixel-perfect recreations of trademarked UIs. Use original assets that *evoke* the era; do not ship Windows XP screenshots, the Luna chrome, or copyrighted sound effects. The "Windows XP" theme is more like "early-2000s desktop." The "Pixel Art" theme uses a generic 8/16-bit aesthetic, not Mario or Pokémon sprites.

## 12. Vector embeddings

Two distinct embedding columns per question, both **3072-dim float32 vectors**:

- **`classification_emb`** — used by smart difficulty's novelty feature (§13.1).
- **`similarity_emb`** — used by `get_similar_questions(question_id, k)` to rank questions by cosine similarity.

In the current seed, both columns hold the same vector (produced by `gemini-embedding-002`). The column-pair layout is preserved so a future seed bundle can populate them with different models if needed; the runtime treats them independently.

**Source.** Embeddings are produced **outside this codebase** by the project owner's dev-cycle pipeline (Gemini API, batched, with whatever model versioning policy the owner adopts). They ship in `pre_db.embeddings.npz` (§4.1). The runtime app **never** generates, refreshes, or invalidates embeddings; it only loads and reads them.

**Storage.** `BLOB` of float32 little-endian (3072 × 4 = 12 288 bytes per embedding per question; ~24 KB per question for the pair). At 100k questions that's ≈ 2.4 GB total — acceptable on disk. Brute-force similarity does a streaming dot product against the live BLOB column; no in-memory matrix.

**Diagnostic field.** `configs.EMBED_MODEL_VERSION` records the model version string (e.g. `"gemini-embedding-002"`), copied verbatim from the seed bundle's metadata. The Settings → Data card surfaces it as a read-only readout.

**Augmented questions.** Rows added via §4.2 have NULL embeddings. `get_similar_questions` skips them silently (returning fewer than `k` if necessary). They will gain embeddings when the project owner ships an updated seed bundle that includes them.

## 13. Smart difficulty (Phase 2)

### 13.1 The score

A normalized difficulty score in `[0, 20]` derived per topic from three sub-scores. **All three inputs are local computations over seed-supplied data — no API calls.**

- **Solution length** — derived from the pre-baked `solution_outline` column (§13.2): count the top-level items in the outline. Top-level items are non-trivial steps by construction. Questions without an outline (the bottom 70% by length, plus augmented rows) get a sub-score of 0.
- **Solution novelty** — how rare the *approach* is. Use the classification embedding: `1 - max_cosine(this, other questions in same subtopic)`. Questions without an embedding get a sub-score of 0.
- **Subject-matter depth** — looked up from `configs.TOPIC_DEPTH_MAP`, which is loaded from `pre_db.topic_depth.json` at ingest (§13.3).

A per-topic learned function combines the three into the final score. The model trains via pairwise comparisons: the user is shown two questions and says which is harder and by how much; gradient descent on a simple linear or small MLP head updates the per-topic weights. **The pairwise trainer is the only learned component, and its data comes entirely from in-app user feedback.** No external service is involved.

This entire feature is **Phase 2** and gated behind a Settings toggle.

### 13.2 Solution outline format and ingestion

A **solution outline** is an enumerated sketch of how to solve a question, used both for the difficulty score (§13.1) and as a user-facing PDF rendering option (§6.5, "Outline only").

**Outlines are pre-generated externally during the dev cycle** by the project owner (using whatever LLM and prompt the owner prefers) and shipped in `pre_db.outlines.json`. The runtime app does not generate outlines, has no LLM client, and has no "Regenerate outline" affordance anywhere in the UI.

The runtime app's responsibilities are limited to: ingesting the file (§4.1), rendering outlines into PDFs when "Outline only" is selected, displaying outlines in the Browser side panel (read-only), and counting top-level items for the smart-difficulty length sub-score.

**Format the project owner is targeting** (informational; the runtime parses it as opaque LaTeX):

- **Top-level items:** non-trivial steps / skills / methods / goals. The general procedure being applied, named as specifically as possible without including problem-specific numbers. Acceptable: "Apply induction on `n`", "Recognize the integrand as a Gamma integral", "Diagonalize the matrix". Unacceptable as top-level (these belong as children, if anywhere): "Plug into formula", "Identify the variable".
- **Children:** subgoals required to complete the parent step. May themselves be substantive ("Verify the base case `n = 1`") or mechanical.
- **Numbers and variables:** problem-specific numerical values are omitted; named procedures are preferred. Variable names may appear when essential to identify the method.
- **Multi-part questions:** a single shared-technique outline.
- **Multi-solution questions:** one outline (the canonical / first solution).

**Eligibility (in the dev pipeline):** the top 30% of questions by raw `solution` character length. Shorter solutions don't get outlines and the runtime's "Outline only" path falls back to the full solution for those rows (§6.5).

### 13.3 Per-topic depth map

A persistent JSON mapping `topic → integer depth in [0, 20]`, stored in `configs.TOPIC_DEPTH_MAP`. Loaded from `pre_db.topic_depth.json` at ingest. It is **read-only at runtime**; the project owner regenerates it during the dev cycle if topics are added or judged differently.

(There is no in-app editor for the depth map. If the user wants to override values, they must do so by shipping a new seed bundle. This is a deliberate simplification consistent with the "no runtime authoring" rule.)

## 16. Non-goals

- **No web/mobile build.** Desktop only.
- **No multi-user / auth / cloud sync.** Single user; everything local.
- **No internationalization shipped** in MVP. English only — but **i18n scaffolding** (string keys + a single `en.json` locale file with all UI strings keyed) is in scope so adding languages later does not require touching every component.
- **No accessibility audit gate** in MVP, but: keyboard navigation must work for the form controls, and color contrast in the default themes must be ≥ WCAG AA. Themed flavors (Pixel Art etc.) are exempt — they're opt-in. Themed flavors get an "Accessibility mode" toggle that forces high-contrast text on top of the theme's background art.
- **No runtime question authoring.** Question content is not editable, creatable, or deletable from inside the running app. The only paths by which questions enter the DB are the shipped seed bundle (§4.1) and user CSV augmentation (§4.2). There is no Author mode.
- **No runtime LLM, embedding, or other external API access.** All derived data (vector embeddings, solution outlines, the per-topic depth map) is **pre-generated externally** during a dev-cycle pipeline that is out of scope for this codebase, and shipped as seed data. The runtime makes no outbound network calls.
- **Question generation from arbitrary content** — out of scope. The project owner has separately scoped a "Human Question Generator" project; this codebase does not integrate with it.
- **Telemetry / phone-home / crash reports** — none.
- **Auto-update.** Manual installer. Future versions may ship an updater.
- **No matplotlib.** Hard rule.

## 17. Glossary

- **Topic / Branch / Subtopic** — the three-level taxonomy attached to each question. There is no `Stream`; there is no `Subject` column on `questions`.
- **Subject (alias Course)** — a saved bundle that *points to* topics and optionally excludes specific branches/subtopics. A question is "in a subject" when the subject points to its topic and does not exclude its branch/subtopic, **and** the question's `in_syllabus` flag is `1`. See §3.6. The `subjects` table starts empty; users create subjects manually.
- **In-Syllabus flag** — a per-question manual override (Browser mass-action) that excludes a question from "in syllabus" filters regardless of subject. Independent of subjects.
- **Seed bundle** — the read-only set of files in `app/data/seed/` (xlsx, csv mirror, embeddings npz, outlines json, topic-depth json) that ships with the app. Loaded once on first launch; reloadable from Settings.
- **Augmentation** — the user-side path for adding questions to a running install via a compatible CSV (§4.2). Augmented rows have NULL embeddings and outlines until a future seed bundle includes them.
- **PSet** — one generated PDF, with the metadata to reproduce it.
- **Quiz / Attempt** — Phase 2: a PSet-like artifact for interactive practice; an attempt is one user run-through.
- **PBS** — Physics Brawl Style. A locked interactive quiz template with a parallel widget pool, total-only timer, numerical answers, and difficulty-linear scoring with wrong-attempt decay (§10.1).
- **Template** — a saved snapshot of the Generate form's state.
- **Solution outline** — an enumerated sketch of how to solve a long-solution question; top-level items are non-trivial steps/methods, children are subgoals. **Pre-generated externally** during the dev cycle and shipped as seed data. Used by smart difficulty, by the Browser side panel (read-only), and by the "Outline only" PDF placement option.
- **Multiplicity** — `times_used` for a single question.
- **Multiplicity distribution** — count of questions at each multiplicity level (1×, 2×, …).
