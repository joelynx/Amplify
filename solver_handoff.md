## 1. Goal

Run the existing v5 solution pipeline (until now the Claude Message Batches API,
`pipeline/scripts/run.py`) on the owner's **Claude subscription**, with **no drift**
from the API run:
- same system prompt, byte for byte;
- same user message, model (`claude-opus-5-5`), adaptive thinking and checks;
- same storage and attribution line.

Two deliberate differences, both owner decisions:
1. **Scope.** Math questions whose own `solution` is **missing** or a **Gemini** one
   (`[Generated by gemini-...]`) and that have no generated solution yet.
2. **Hard sources.** 14 sources run at **high effort with a 128k output cap**, and
   **every question in them is redone**, including the ones the API already solved at
   medium.

## 3. What was built

`pipeline/scripts/run_sub.py`:
- **One process per question.** Each question is a fresh single-turn `claude -p` process.
  It calls the native binary
  `%APPDATA%\npm\node_modules\@anthropic-ai\claude-code\bin\claude.exe`; the npm
  `.cmd` shim would mangle arguments on Windows.
- **Flags.** `--system-prompt-file`, `--model claude-opus-5-5`, `--effort <medium|high>`,
  `--tools ""`, `--output-format stream-json --verbose`, `--no-session-persistence`,
  `--strict-mcp-config`, `--safe-mode`, `--permission-mode dontAsk`.
- **Working directory.** `~/.amplify-subscription-solver`, a fixed empty folder outside
  any git repository. Claude Code describes the folder in the request, so it must not
  change between questions.
- **Environment.**
  - It drops every inherited `ANTHROPIC_*` / `CLAUDE_*` variable. An API key would
    bill the API, and a parent session's `CLAUDE_EFFORT=xhigh` would leak in.
    `CLAUDE_CODE_GIT_BASH_PATH` is the only one kept.
  - It sets `CLAUDE_CODE_MAX_OUTPUT_TOKENS`: 32000, or 128000 at high effort.
  - It sets `CLAUDE_CODE_THINKING_DISPLAY_UPDATES=0`, which makes the thinking request
    plain `{"type":"adaptive"}`, the API default.
  - It sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` and `DISABLE_AUTOUPDATER=1`.
- **Replies.** Stored exactly where an API download goes: `pipeline/outputs/<qid>/`
  gets `solver_<n>.tex` and `response_<n>.json` (with `"transport": "subscription"`).
  The status becomes `received`, and the usage row gets `batch_id = 'sub:<session>'`.
  `run.py`'s spend figures exclude these rows. **`run.py judge` then validates,
  assembles and writes them unchanged.**
- **Retries.** A reply that fails the checks becomes `retry` with feedback, exactly as
  in the API run. The next `solve` sends those first (attempt 2). A second failure goes
  to `needs_human_review`.
- **Images.** Questions with `\includegraphics` or prose pointing at a figure are
  skipped (`skipped_image`), the same rule as the API run.
- **Usage limits.**
  - A usage-limit refusal costs nothing: the question goes back to the front of the
    queue.
  - Without `--wait-on-limit` the run stops; with it, the run sleeps until the reset.
  - A Claude Code version change or an API-key login stops the run.
- **Lock file.** `pipeline/run_sub.lock` (git-ignored) prevents two concurrent `solve`
  runs. After a crash: `--force-unlock`.

Commands, all from the repo root (Windows Git Bash; use `uv run python -I`):

```
uv run python -I pipeline/scripts/run_sub.py verify          # free, no usage: capture the real request on a local stand-in server, check it
uv run python -I pipeline/scripts/run_sub.py status          # per source: effort, done, retry, redo, todo
uv run python -I pipeline/scripts/run_sub.py queue --n 30    # next questions in order
uv run python -I pipeline/scripts/run_sub.py solve --ids 1,2,3          # pilot: exact ids
uv run python -I pipeline/scripts/run_sub.py solve --wait-on-limit      # full run (background it; log to pipeline/run_sub.log)
uv run python -I pipeline/scripts/run.py judge                          # XeLaTeX + KaTeX checks, assemble, app-db writes (ASK FIRST)
```

### How "no drift" is enforced

- **`verify`** sets `ANTHROPIC_BASE_URL` to a local stand-in HTTP server, runs Claude
  Code exactly as `solve` would, and checks the captured request field by field. It
  runs 4–5 sample questions:
  - a fresh question;
  - an API retry, whose message carries the previous reply;
  - a non-ASCII question;
  - a medium-effort and a high-effort question.
- **What it checks:**
  - The login is the subscription (`apiKeySource=none`).
  - The system prompt's sha256 equals the one all 16 API batches used
    (`3d8c416ccd5db239...`). The prompt and the question arrive byte for byte.
  - Model, effort and `max_tokens` match.
  - Thinking is adaptive, there are no tools and no extra request fields, and there is
    exactly one model request.
- **Unavoidable wrapping.** Claude Code adds fixed text a subscription login can't switch
  off:
  - a billing line;
  - `You are a Claude agent, built on Anthropic's Claude Agent SDK.`;
  - a `<system-reminder>` with the account email before the question;
  - a trailing `# Environment` system message: folder, OS, model, date and
    `<total_tokens>`.

  Its fingerprint, with the date excluded, is **`38ebe356ea7c987b`**. The owner
  **accepted** it on 2026-11-04 for Claude Code **2.1.296**; it's stored in pipeline.db,
  table `sub_verifications`.
- **Before every run.** `solve` re-runs `verify` and refuses to start unless that
  fingerprint is accepted. If Claude Code has updated and the fingerprint changed, show
  the owner the new boilerplate (`pipeline/outputs/_sub_verify.json`). Only after they
  agree, run `verify --accept`.

### Redo mechanics (hard sources)

- **When.** A question in a source listed in `subscription.effort_by_source` is redone
  when its stored generated solution, or its latest attempt, came from a lower effort.
  The effort is read from the attribution line `[Generated by Claude Opus 5.5 at medium
  effort]` or from `status.solverN_effort`.
- **What `solve` does at the moment it sends the question:**
  - moves the old files to `outputs/<qid>/before_high_redo_<timestamp>/` (kept, not
    deleted);
  - resets the status row to a fresh attempt 1.
- **Until the redo passes.** The app keeps showing the medium solution.
- **Answer and Hint cells.** New helper `common.pipeline_wrote()`. A value the
  pipeline itself wrote earlier:
  - may be replaced by the redo (`assemble.py`, `apply_fields.py`);
  - is no longer used as a reference answer, and no longer blocks a new hint
    (`run.py judge_one`).

  Values from the source or the owner are never touched.

## 5. Pre-flight checklist for the new session

1. **Wait for the reference fixes.** The owner is fixing missing references (theorems,
   figures, other-exercise references) in another session. Confirm with the owner that
   it is **finished** and that nothing else is writing amplify.db.
2. **Find what changed.** Compare current question texts against the snapshot
   `pipeline/archive/question_text_snapshot_20261104.json` (qid → `[sha256(latexcode)[:16],
   sha256(solution)[:16]]`, taken before those fixes).
   - Report how many questions changed, by source, split into:
     - still in the queue (fine: the run reads the current text);
     - **already solved by the API from the old wording**, outside hard sources
       (hard sources are redone anyway).
   - Ask the owner whether that second group should be redone. That needs a small code
     addition: e.g. a `subscription.redo_ids` list treated as stale once, so they don't
     loop.
   - Also report questions whose fix **added** a figure: they now count as image
     questions and will be skipped. Questions where a figure was **transcribed** into
     text become solvable.
3. **Re-check what the earlier session left.** Run `git status` (are the changes
   committed?), then `run_sub.py verify`, which must end with `accepted`. Then run
   `run_sub.py status` and `queue`.
4. **Back up both databases**, with timestamped copies:
   - `app/data/appdata/amplify.db` → `amplify.db.bak-<date>-pre-subscription-pilot`;
   - pipeline.db, using sqlite's backup API (it's in WAL mode), into `pipeline/archive/`.
5. **Ask the owner for the go-ahead on the pilot.** Pick about 20 ids by hand, spread out:
   - 2 API retries;
   - 2 Gemini replacements (IIT);
   - 4 new-book questions (e.g. Strang, Blitzstein, Bertsekas, Oksendal);
   - about 12 hard-source questions: Miklos ×2, Selection Tests ×2, Engel,
     Austrian-Polish, Orchard, Winkler ×2, Levitin, Toronto, Leningrad. Mix redos and
     never-solved ones.

   Then run `solve --ids ...`, then (after asking) `run.py judge`. Show the owner a few
   `outputs/<qid>/final.tex` files, including at least one high-effort redo next to its
   `before_high_redo_*/final.tex`.
6. **Full run, on the owner's go:** run `solve --wait-on-limit` in the background, logging
   to `pipeline/run_sub.log`. Run `run.py judge` periodically, without `--watch`, which
   can loop on the old retries. Judge uses XeLaTeX; the README says to run XeLaTeX at
   below-normal priority. Use `run_sub.py status` for progress.
7. **Afterwards:**
   - Every replaced or new `generated_solution` makes its embedding stale. Re-embedding
     is `app/tools/reembed.py`: `--dry-run` first, Gemini credit, **ask first**.
     Question-only rows stay unembedded by owner rule; newly solved rows become
     embeddable.
   - Update the memory file `project_subscription_solver.md`.
   - Commit only if asked.

## 6. Why these sources are "hard" (research of 2026-11-04, summary)

The analysis scripts lived in that session's scratchpad and are gone; the numbers are here.

- **API run (Opus 5.5, medium, 11,310 replies).**
  - Retries were almost all LaTeX-format failures; AIME answers were wrong 2 of 676.
  - 44 replies hit the 32k cap: Miklos 10 of 100, Selection Tests 7, Winkler 9, Engel
    5, Sedrakyan 4, Orchard 3, Levitin 3, Mladenovic 2, Stirzaker 1.
  - Median thinking tokens: Miklos 2,760 (p90 28k), Selection Tests 1,394, Austrian-Polish
    1,145, Tripos 1,004, Orchard 912. Textbook and exam sources sat at about 400–550.
  - By topic, the heavy tails were combinatorial geometry, games and extremal
    combinatorics.
- **Literature.** Final-answer competition maths is near-saturated for current Claude
  models. The failures are:
  - proofs (Opus 4.6: 96.7% AIME 2026 vs 47% USAMO 2026, MathArena);
  - combinatorics constructions and games, and geometry/diagrams;
  - altered versions of famous problems (PutnamGAP: Opus 4 fell from 26.5% to 13.8% on
    kernel variants);
  - truncated reasoning.

  More effort helps on hard problems, with gains flattening between high and max.
- **A blind classification** of 48 sources from 10 sampled questions each agreed with
  the above. It also flagged statements that cite missing context: Oksendal 48%,
  Dekking 36%, Strang 19% (+16% fill-in-the-blank), IITR 11 of 103 fragments. Figures:
  Levitin 28%, Erikson 23%, Winkler 10–12%. That is what the owner is fixing now.
- **Embedding density is not a usable novelty or difficulty measure** for this bank.
  - Spearman correlation with thinking tokens is about 0, overall and within sources.
  - The vectors cluster by **who wrote the solution** (rows embedded from Claude's
    solution have 99% Claude-solution neighbours) and grow with how big a source is.
